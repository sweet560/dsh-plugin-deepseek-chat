# 全自动投递通道 · 使用介绍（基于 2026-11-19 真机全流程）

> 本文按当天实际产生的全流程截图与 DSH leveldb 落盘 trace 编写，对应插件 **v1.4.6（全自动流程初步真机验证通过）/ DSH 0.2.2-rc.5**。所有流程描述均可在截图与 trace 中逐条对照。
>
> > 注：截图中「DONE + `<TO_DEV>任务已完成</TO_DEV>` 被回投、两次重复、最终 180s 超时」是 **v1.4.4 及之前**的行为；v1.4.5 已将「区块内纯完成语义」判为 done 终止，不再回投，v1.4.6 进一步修复错误词误判、决策卡观感与停机流程，详见文末「修复方向」。

## 1. 它解决什么问题

把三方串成一条自动闭环：

- **网页 chat（思考与审核 agent）**：本次真机为豆包 `https://www.doubao.com/chat/`，负责出任务、审结果。
- **DSH 桌面会话（开发 agent）**：负责干活、产出文件。
- **你（决策者）**：决定启动与终止，随时接管。

目标：网页出一条任务 → 自动投递到桌面 → 桌面做完自动回投网页审核 → 网页说"完成"或给新任务 → 如此循环，直到完成或需要你介入。网页全文**不投递**，只传 `<TO_DEV>…</TO_DEV>` 里的片段，省上下文、省 Token。

## 2. 先记住这几个约定

| 名称 | 作用 |
| --- | --- |
| 定界符 `<TO_DEV>` / `</TO_DEV>` | 只有区块里的内容会传给对方；区块外一律不传 |
| 完成词 `DONE` / `完成` / `通过` / `APPROVED` | 表示"任务做完了" |
| 重启词 `重启 DSH` / `restart DSH` 等 | 命中即暂停，等你处理 |
| 用户介入词（handoff）`请重启宿主验收` / `宿主验收` / `请用户验收` / `需要你本人` / `需要人工介入` 等 | 命中即暂停弹卡，必须由你本人接入 |
| 输出契约 | 插件自动附加在推送文本末尾，要求审查 agent 按格式回复 |
| 状态栏按钮 | `▶ 启动全自动` / `■ 停止全自动`；设置页第 5 张卡「全自动投递通道」可配置定界符、三类关键词、输出契约、自动提交开关 |

## 3. 完整使用流程（对照截图逐步骤）

1. **网页端设定角色与任务**（截图 m00204）：你在网页 chat 输入框写明"你是思考和审核 agent，把要交给开发 agent 的内容放进 `<TO_DEV></TO_DEV>`；若已完成就发 `<TO_DEV>任务已完成</TO_DEV>`"，并给出任务目标（本次是"极简 C 语言爱心 + HTML 展示，适配初学者"）。
2. **网页审查 agent 给出任务目标**（截图 m00204、m00210 左侧）：把需求、文件清单、`heart.c` 参考实现放进 `<TO_DEV>` 区块。
3. **桌面端此时只有角色设定**（截图 m00206）：你最初发给桌面的那句"你将作为一个开发 agent…"里没有任务，开发 agent 如实回复"还没有给出具体任务目标，请告诉我"——**任务此时还没到桌面**。
4. **点 `▶ 启动全自动`**：插件把网页 `<TO_DEV>` 区块内容自动投递进桌面会话（截图 m00208），开发 agent 收到"任务目标：实现一套极简 Demo…"。
5. **开发 agent 干活**（截图 m00212）：生成 `heart.c` / `heart.html` / `README.md` 三个文件（在 `heart-demo\` 目录），回复"三个文件已全部生成完毕（gcc 不可用跳过编译）…"。
6. **自动回投网页**（截图 m00210 右侧、m00214）：桌面 `turn/end` 触发，把开发 agent 的回复 **+ 输出契约**一起推送回网页，请审查 agent 审核。
7. **网页审查 agent 回复完成**（截图 m00214、m00218）：`DONE\n<TO_DEV> 任务已完成 </TO_DEV>`。
8. **⚠️ 异常点**：本应就此结束，但流程把它判为"继续"，把"任务已完成"当成新任务又回投给桌面（截图 m00216），开发 agent 只好回"好的，任务已全部完成…"。
9. **网页再次回复相同的** `DONE <TO_DEV> 任务已完成 </TO_DEV>`（截图 m00218，与第 7 步内容完全相同，均来自 13:24）。
10. **卡住并超时**（trace 05:27:16Z）：进入"等待网页回复超时"，你手动点 `■ 停止全自动`（trace 05:29:18Z）收尾。

## 4. 谁来判定"继续还是停"

判定中枢按优先级从高到低：

```
done（完成词）→ restart（重启词）→ handoff（用户介入词）
→ duplicate（与上轮重复）→ error → max-loops → no-marker → continue
```

其中一条关键规则：**定界区块优先**（`lib/client.js:958-968`）——只要回复里有合法非空的 `<TO_DEV>…</TO_DEV>` 区块，就提炼区块当作新一轮任务，`<TO_DEV>` 区块外散落的完成词 `DONE` / `完成` **不算数**。这正是本次异常的根因（见第 6 节）。

## 5. 终止与接管方式

- **自动结束**：完成词被识别为 `done`（前提：回复里没有 `<TO_DEV>` 区块）。
- **暂停弹决策卡**：命中重启词 / 用户介入词 / 重复 / 错误词 / 超过最大轮数时，弹卡让你选：继续 / 编辑 / 重试 / 终止。
- **人工兜底**：任何时候点 `■ 停止全自动`，流程退回条件触发闭环。
- **排查工具**：落盘的 loop trace 键为 `dsh-plugin-deepseek-chat:loop-trace`（存于 `Local Storage/leveldb/`），记录了每一步 stage 与时间。

## 6. 本次实际流程核验：发现的问题

证据：截图 m00204–m00218 + leveldb trace（UTC，北京时间 +8）。

| # | 问题 | 客观证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **完成语义被误判为 continue（核心 bug）** | 网页审查 agent 回复 `DONE\n<TO_DEV> 任务已完成 </TO_DEV>`（截图 m00218、trace 05:24:10Z `lastResponsePreview`）。`extractPilotPayload` 定界区块优先（`lib/client.js:958-968`），提炼出 payload=`任务已完成`、state=`ok`（**不是 done**）；`classifyPilotReply` 判 `continue`（`lib/client.js:1054`）；`pilotAutoSubmit=true` 又把"任务已完成"当新任务提交回桌面（`lib/client.js:2082-2087`）。 | 终止语义失效，把"做完了"当成新任务反复回投 |
| 2 | **无效循环 / 重复回复未被有效拦截** | 截图 m00218 中 `DONE <TO_DEV> 任务已完成 </TO_DEV>` 连续出现两次（都是 13:24）；重复检测在 `lib/client.js:1042`，但流程最终走到 timeout 而非 pause。 | 桌面与网页互相回投"任务已完成"，空转至少 2 轮 |
| 3 | **最终超时，只能人工停止** | trace：05:24:15Z 第二轮 `send ok` 后再无 `response-complete`，05:27:16Z `state:timeout`（180s，公式 `DEFAULT_REPLY_TIMEOUT=180000`，`lib/client.js:211`），05:29:18Z 你手动 `pilot-stop`。 | 卡死约 3 分钟，靠人工接管才结束 |
| 4 | **网页平台与插件定位不符** | trace config：`chatUrl = https://www.doubao.com/chat/`，但插件名为 `deepseek-chat`、发布说明以 `chat.deepseek.com` 为准；`lib/client.js:1852` 注释自认"实机两次 180s 超时、不再依赖易变网页 DOM"。 | 抓取链路对豆包适配差，是本次超时的老问题复现 |
| 5 | **发布说明早有预警，本次印证** | v1.4.0、v1.4.4 发布说明均标注"全自动投递通道尚未经过真机完整跑通"。 | 本次真机结果印证：能启动、能投递、能回投，但终止判定有缺陷，无法干净收尾 |

**一句话结论**：全自动通道"跑得起来、收不干净"。根因是"完成词"与"定界区块"两套策略冲突——审查 agent 按契约同时写了 `DONE` 和 `<TO_DEV>任务已完成</TO_DEV>`，插件按区块优先判定继续，把一个明确的终止信号当成新任务回投，导致空转直到超时。

## 7. 使用建议（在不改代码的前提下）

- 想干净收尾，请让网页审查 agent **完成时只写完成词 `DONE`，不要再套 `<TO_DEV>` 区块**（因为一旦有合法区块，区块优先规则会压过完成词）。
- 若审查 agent 必须回区块，区块内请写具体的新任务，而不是"任务已完成"这类终止语义。
- 遇到空转，及时点 `■ 停止全自动`，不要等 180s 超时。
- 想排查时读 `dsh-plugin-deepseek-chat:loop-trace`，关注 `pilot-extract` 的 `detail` 与 `lastResponsePreview`。

## 附：问题修复方向（供决策，本文不改代码）

1. **优先修问题 1**：在 `extractPilotPayload` / `classifyPilotReply` 中增加"区块内文本本身表达完成语义（如'任务已完成'）或与上轮 payload 等价 → 判 done/pause"，而不是无条件 continue。
2. **修问题 4**：确认是否把 `chatUrl` 换回 DeepSeek（`chat.deepseek.com`），或补豆包输入框抓取适配。
3. **修问题 2/3**：增强重复回复在自动提交路径上的拦截，超时前主动弹卡。
4. 按项目约定，若修复需要发新版，**由你弹卡选择版本号**，本文不擅自递增版本。
